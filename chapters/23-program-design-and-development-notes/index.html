23 Program design and development notes¶

☑ For creators ☐ For visitors

This part of the Guide records some of the design decisions and implementation details behind Dynamic Web Extended. It is intended mainly for anyone maintaining or extending DWE in the future.

DWE began as a modification of the Gramps Dynamic Web Report (DWR). Wherever practical, the existing DWR structure and behaviour have been retained. Changes have generally been made to add a feature, improve the presentation of existing information, or deal with a particular limitation encountered while using DWR.

Some decisions described here are not obvious from the program code itself. They are recorded so that a future change does not inadvertently undo behaviour that was deliberately chosen.

23.1 Relationship data: record rather than infer¶

DWE tries to report genealogical relationships that are explicitly recorded in Gramps rather than infer additional relationships from the surrounding family structure.

This is particularly important for step relationships. A person should be described as a stepchild when that relationship has been recorded in Gramps. DWE does not assume that a child becomes the stepchild of somebody merely because a birth parent subsequently forms another family.

The same principle is used when identifying siblings. DWE can find possible siblings by following the parent-child relationships recorded in Gramps, including non-birth relationships. It then uses shared birth parents to classify full and half-siblings. If a sibling connection is found but no common birth parent is found, DWE describes the person as a non-birth brother, non-birth sister or non-birth sibling, rather than guessing that the relationship is a step-sibling relationship.

This distinction is deliberate. Family structure alone is not sufficient evidence for DWE to create a genealogical relationship that the researcher has not recorded.

23.2 Parent-child relationship None¶

An explicit Gramps parent-child relationship of None should not be used for relationship traversal. It indicates that the parent-child relationship does not exist or is considered not to exist, and therefore should not be used to discover parents, siblings or other relatives.

Whether an explicitly recorded None relationship should nevertheless be displayed to a website visitor is a separate presentation question. This remains an area for possible future work.

23.3 Multiple families and siblings¶

DWR already supports people belonging to multiple families. DWE makes some changes to the presentation of these families to make less usual family structures easier to follow.

The Parents & siblings display associates children with the appropriate parent family and can also show other families of a person's parents. The inherited option controlling this behaviour is labelled Include children from other families of the parents in DWE and is selected by default.

This option controls presentation only. It does not alter the genealogy used by other DWE features. For example, clearing the option may hide an additional parent family from Parents & siblings, while Tracking can still identify a half-sibling and Events can still include that sibling's events.

The DWR person-family JavaScript coding was corrected so that parent-family information is matched by the actual family index rather than its position in an intermediate list. This is important when a person has several parent families.

DWE also corrects display problems encountered with families containing children but no recorded parents, and with collapse/expand controls in multiple-family displays. Gramps permits a family containing siblings without requiring an artificial unknown father or mother, and DWE can display such a family correctly.

23.4 Parent-child relationship wording¶

DWE can alter the wording of standard Gramps parent-child relationship types, and a Parent-child relationship note can override relationship wording. The relationship naming supports the inverse, for example ‘Birth’ could be changed to ‘born to’.

DWE does not maintain a table of default relationship phrases. If no Parent-child relationship note is selected, or if a relationship has no matching entry, the relationship name supplied by Gramps is used.

The note is parsed into a dictionary keyed by the Gramps relationship name. The lookup uses the localized relationship name returned by Gramps, allowing entries to be written in the language used to generate the report. Multiple languages can coexist in the same note, and entry order is not significant.

The optional A and P values allow the kinship word to be placed after or before the relationship phrase. This avoids assuming that English word order is suitable for every language.

The user-supplied relationship phrases are not translated by DWE. The website creator is responsible for providing the standard relationship name and the desired wording.

23.5 Translation and Local Labels¶

New interface text intended for translation follows the translation mechanism already used by Gramps. DWE-specific strings are added to the translated-label data where they are required by the generated JavaScript.

Local Labels is a separate mechanism. It allows the report creator to replace translated labels without modifying DWE. Replacement occurs after the normal label has been translated, so the label on the left of a Local Labels definition must correspond to the label in the language being used for the report.

A Local Labels replacement is global to that translated label; it is not associated with one particular page or control. For this reason, a developer should not reuse the same translated string for unrelated purposes merely because the English wording happens to be identical.

23.6 Topola Tree Viewer¶

The Tree Viewer is based on Topola Viewer. DWE uses a locally bundled build rather than depending on the online Topola service. The built application is stored under vendor/topola-viewer/dist.

Bundling Topola keeps the generated website self-contained, does not send the family GEDCOM to an external viewer, and avoids cross-site and CORS (Cross-Origin Resource Sharing) issues that can arise when the DWE website and the viewer are hosted at different locations. The Tree Viewer and its supporting files are served from the same website as the rest of the DWE report.

DWE generates the GEDCOM only when Include Tree Viewer is selected. The GEDCOM is generated using the Gramps GEDCOM writer and is then sanitised for use by Topola. DWE removes the generated submitter reference, submitter record and generated copyright header so that researcher details are not unnecessarily included in the Tree Viewer data.

DWE's bundled Topola build has also been customised. Among the changes are integration with the DWE person pages, person highlighting, and renaming the export filenames.

Changes to Topola source code are made in the separate Topola source/build directory and rebuilt before the resulting dist files are copied into DWE. Consequently, a future upgrade of Topola must preserve or reapply the DWE modifications rather than simply replacing the bundled files with a new upstream build.

23.7 Tree Viewer limitation¶

Tree Viewer may fail to render large trees. It appears that Topola is in the process of developing expandable tree controls. This is a path for further investigation. If the Viewer could initially display a limited number of generations and expand the tree on demand, it might avoid the need to render a very large tree at once.

23.8 Lifespans and Vega¶

The Lifespans display uses Vega rather than the normal DWR charting code.

DWR generally exports small individual categories of information into separate JavaScript data structures and combines them in the browser. The Lifespans implementation takes a somewhat different approach: much of the information needed to construct a person's timeline row is assembled together for the chart. This was a deliberate implementation choice because the timeline needs several related values at the same time.

Lifespans is person-oriented rather than family-oriented. The chart gathers the subject's parents, siblings, spouses and children and arranges them into those groups. People are de-duplicated where necessary.

Vega export is configured to use lifespans as the download filename and a white chart background, so exported SVG and PNG files have predictable filenames and appearance.

23.9 Markdown processing¶

DWE supports three ways of identifying Markdown: the fixed first-line MD marker, a selected Markdown note type, and the Treat ordinary notes as Markdown option.

MD is deliberately a fixed marker rather than a configurable string, making marked notes portable between DWE installations and family trees.

Html code and To Do notes always take precedence over the Markdown mechanisms and are excluded from Markdown processing.

DWE preserves Gramps styled-note formatting and then allows Markdown processing of the resulting content. This permits useful combinations such as a Markdown table within an otherwise normally styled Gramps note. Because Gramps styling and Markdown are two independent formatting systems, unusual combinations may still need to be checked in the generated website.

23.10 Gramps styled-note compatibility¶

Gramps 5.2.3's HTML backend does not provide mappings for the Strikethrough and Subscript StyledText types. As a result, the original DWR can fail when it encounters notes containing those styles.

DWE uses its own small extension of the Gramps HTML backend to provide HTML mappings for these styles (\<s> and \<sub>). This retains compatibility with Gramps 5.2 while allowing the normal Gramps implementation to handle the other StyledText types.

23.11 Participation events labels¶

Participation event labels are two-line labels displayed like this: Marriage followed by (:Best man) for a person with a ‘Best man’ role. The colon identifies participation roles, in case parentheses may be part of an event type name, such as Marriage (Christian).

23.12 Diagnostic logging¶

DWE uses the Gramps/Python logging system for development diagnostics.

Normal diagnostic messages should use DEBUG level so that they do not interfere with ordinary Gramps operation. WARNING and particularly ERROR should be reserved for conditions that the user needs to know about; Gramps may present ERROR messages through its error-reporting interface.

Logging output appears in the console when Gramps is started from the console.

23.13 Development and source control¶

DWE is maintained as a Git repository. Development changes should normally be made in a separate branch, tested by generating and viewing a report, and committed in small, logical checkpoints.

Generated websites should be tested through a local HTTP server rather than solely with file:// URLs. Some browser features, including the Tree Viewer, require normal web-server behaviour. DWE provides View report locally.bat for convenient local viewing on Windows.

Changes involving bundled third-party components such as Topola should distinguish between changes to the upstream source and the built files stored in the DWE repository.

23.14 Browser storage¶

Some DWE display preferences are saved in the browser so that they can be remembered as the visitor moves between pages or returns to the website later.

Web browsers provide two similar forms of storage that can be used for this purpose:

Session storage retains information for the current page session. It can carry a setting between pages while that session continues but is not intended to persist as a long-term preference.

Local storage persists beyond the current browser session. It allows a website to remember a preference when the visitor closes the website and returns to it later.

DWE uses browser storage for some visitor display preferences rather than storing them in the generated family-history data. These settings therefore belong to the browser being used, not to the Gramps family tree or the DWE report options.

Browser storage must be permitted for these preferences to be remembered. Most browsers allow it by default. Private or incognito browsing, clearing site data, or privacy settings that remove or prevent site storage may cause preferences to be lost.

These browser-stored preferences should not be confused with the report options used when generating DWE. Report options are saved in a file by Gramps for the family tree; browser preferences are choices made while viewing the generated website.

23.15 Additional CSS and JavaScript¶

DWE retains the CSS and JavaScript structure of the original Dynamic Web Report and adds or modifies files to support its additional features.

The dwr_start.js file loads the JavaScript and style sheets used by the generated website. In addition to the standard DWR files, DWE loads dwr_styles_B.css, which contains additional DWE styling, and timeline-vega.js, which contains JavaScript used for the Lifespans display.

Much of the DWE website behaviour is implemented in the existing DWR JavaScript structure rather than in separate files for every DWE feature. For example, DWE additions to person pages and other displays are integrated with the existing dwr.js processing.

Keeping the additional Lifespans code in timeline-vega.js helps separate the Vega-based graphical display from the larger dwr.js file. Additional DWE CSS in dwr_styles_B.css similarly allows DWE-specific presentation changes to be kept separate from the main DWR style sheet.

23.16 Generated website data files¶

DWE reuses the architecture of the original Dynamic Web Report in which much of the genealogical information used by the website is exported into JavaScript data files. The browser uses this data to construct person, family and other displays dynamically rather than requiring a separately generated HTML page containing all the information for each person.

DynamicWebExtended.py exports the principal Gramps objects into JavaScript data structures. These include individuals, families, places, sources, citations, repositories and media. References between objects are generally stored as indexes into the corresponding data structures; for example, an event can contain a place index and citation indexes rather than repeating the complete place and citation records.

DWE extends some of the data inherited from DWR to support its additional features. Person data, for example, includes information used for Lifespan, Why Me, Tracking and Story, as well as the existing person and event information.

Tree Viewer is somewhat different. When Include Tree Viewer is selected, DWE also generates a GEDCOM file for the bundled Topola viewer. This is separate from the JavaScript data used by the normal DWE pages. Before the GEDCOM is included in the generated website, DWE removes the Gramps researcher/submitter information and the automatically generated copyright statement.

The generated website therefore contains both the program files that provide the browser interface and generated data representing the selected family tree. These files belong together: when a generated DWE website is copied to another location or uploaded to a web server, the complete generated directory should be copied.

The generated data filenames reflect these object types. I represents individuals (persons), F families, P places, S sources, C citations, M media and R repositories. The data is divided further into files containing particular fields. For example, dwr_db_I_birth_date_0.js contains extracted birth-date data for individuals. If the data for a field is sufficiently large, it is split across a series of numbered files, such as ..._0.js, ..._1.js, ..._2.js and so on.

23.17 Themes¶

The original DWR uses the bootstrap system to create its website pages. DWE includes a range of Bootstrap themes from Bootswatch that the creator can choose from to generate the site. A site visitor also has access to the same range of themes, so the visitor can easily override the theme and hence the look of their website by choosing another from the Configuration page.

23.18 Notable records — records library¶

The Notable records feature is based on the Gramps librecords.py library, which provides the calculations used to identify individuals and families holding various genealogical records.

DWE currently uses a modified local copy of this library, named dwe_records.py, rather than importing the standard Gramps library directly.

The local version incorporates two improvements:

  • Person with most marriages: Adds a new record category identifying individuals with the greatest number of marriages.

  • Alphabetical sorting: Sorts individuals and families alphabetically when multiple records have the same ranking, providing a consistent and predictable display order.

Both improvements have been submitted to the Gramps project as pull requests:

  • PR #2567 — Person with most marriages

  • PR #2570 — Sort tied Notable Records alphabetically

The intention is to use the standard Gramps librecords.py again once these improvements have been incorporated into Gramps and are available in the supported versions.

The original import statement has been retained as a comment in DynamicWebExtended.py to make this future change easier.

DWE also uses a database adapter to restrict record calculations to the individuals and families included in the generated website, ensuring that the report's privacy and living-person settings are respected.

23.19 Calendar birthday names¶

The rules for determining the surname displayed for married women in Calendar birth events are described in the Calendar Options section.

DWE has retained the surname-selection rules from the original Gramps Web Calendar report. The apparent intention is to allow women to be identified by either their own surname or a surname acquired through marriage.

However, determining an appropriate surname is not straightforward, particularly when a woman has multiple marriages or several recorded names. The inherited implementation represents a compromise, using the woman's recorded names and the order of her families in Gramps. The resulting surname may not necessarily be the one she used at the time of a particular event.

23.20 Known issues and future work¶

Areas identified for possible future work include:

  • None relationships - deciding whether explicitly recorded None parent-child relationships should optionally be displayed, while continuing to exclude them from relationship traversal;

  • Help page in DWE report options dialog - reviewing the DWE help-page destination rather than retaining the original DWR help link. The help page link is hard coded inside Python – the existing report points it to the original Dynamic Web report help page. I would need to adapt that at some time and point this to its own page;

  • Hyperlink display- reviewing the visual treatment of hyperlinks where themes do not make clickable text sufficiently obvious;

  • Version testing - testing DWE against future Gramps versions in an isolated environment before declaring them supported;

  • Local server window - automatically closing of the local server command window after a user closes the DWE browser page;

  • Optimise media file copying - improving the copy_file() function to avoid unnecessary copying of unchanged files. Currently, DWE (and DWR) copies each source file to a temporary destination and then compares its contents with the existing file, even when the files are identical. Consider using file size, modification timestamps or other methods to identify unchanged files before copying, while ensuring that modified files are reliably detected. This could significantly reduce report generation time for websites containing large numbers of media files, particularly when regenerating an existing website.
